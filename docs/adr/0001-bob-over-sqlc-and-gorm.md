# ADR-0001: Bob をデータアクセスライブラリとして採用（sqlc・GORM に優先）

- **ステータス**: 承認済み
- **日付**: 2026-02-08
- **関連 ADR**: ADR-D001, ADR-D007 (DECISION_LOG.md)

## コンテキスト

Broth のデータアクセス層を選定するにあたり、Go エコシステムの主要な選択肢（database/sql 直接使用、sqlc、SQLBoiler、GORM、Bob）を評価した。

設計原則 P1（Go イディオム）により、以下の要件が前提となる：

- パブリック API に `interface{}`/`any` を使用しない
- リフレクションに依存しない（コード生成を優先）
- データベースファースト（スキーマからコードを生成）

## 検討した選択肢

### D1: SQLBoiler フォーク
SQLBoiler のメンテナ自身がメンテナンス終了を示唆しており、コードベースの改善も見込めない。

### D2: Bob を依存として採用（**採択**）
Bob は SQLBoiler のメンテナが後継として開発。`interface{}` をパブリック API に使わず、コード生成ベースでリフレクション不使用。テストファクトリ生成や手書き SQL のコード生成機能も備える。

### D3: Bob フォーク
Bob のメンテナンスが停滞した場合のフォールバック。現時点では不要。

### D4: Bob エコシステムへのコントリビュート
Broth の要件で Bob に不足がある場合、アップストリームに貢献する。D2 と併用。

### D5: GORM（**却下**）
以下の技術的理由で却下：
1. 全主要メソッドが `interface{}` を受け取り、コンパイル時型チェックが不可能
2. 実行時リフレクションに全面依存（5-6 倍の性能劣化）
3. 暗黙的な挙動（ソフトデリートのデフォルト有効化、AutoMigrate の制約）
4. デバッグ困難・IDE サポートの劣化

## 決定

**Bob（D2 + D4）** を採用。`broth/db` で Bob を薄くラップし、`bob.Executor` をトランザクション伝播の基盤とする。

## 根拠

- sqlc は Phase 1 の初期候補だったが、JOIN 結果がフラット構造にマッピングされる制約、動的クエリの困難さ、CRUD ボイラープレートの多さが課題だった
- Bob は sqlc の長所（型安全・SQL ファースト）を持ちつつ、リレーション対応・ファクトリ生成など sqlc の弱点を補完する
- Bob は pre-v1（v0.30.x）だが Broth も pre-v1 であり、API の不安定性は許容範囲

## 影響

- `broth/db` パッケージが `bob.DB`/`bob.Executor` をラップ
- `bobgen-psql` によるコード生成ワークフローが標準に
- Repository 実装は `bob.Executor` を受け取る（トランザクション透過参加）
