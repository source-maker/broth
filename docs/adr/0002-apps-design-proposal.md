# ADR-0002: Django apps 概念の段階的導入設計

- **ステータス**: 提案（Phase 1 では不採用、大規模化時に再検討）
- **日付**: 2026-02-09
- **関連 ADR**: ADR-M006, ADR-005 (DECISION_LOG.md)

## コンテキスト

現在の `modules/` フラット構造はモジュール数 1〜8 では十分だが、9 モジュール以上に成長した場合にグルーピングの必要性が生じる。Django の apps アーキテクチャを調査し、Go のパッケージシステムに適合する形での導入を検討した。

## 提案する構造

```
apps/
├── commerce/           # アプリ（ドメイン境界）
│   ├── product/        # モジュール
│   ├── order/
│   └── internal/       # アプリ内共有（外部アクセス不可）
├── identity/
│   ├── account/
│   └── profile/
modules/                # 小規模プロジェクト用（併存）
└── greeting/
```

## 設計判断（5 件）

### APP001: modules/ と apps/ の共存
- **決定**: 両構造を併存可能とし、段階的移行パスを提供
- **根拠**: 小規模プロジェクト（1〜5 モジュール）に apps/ を強制しない

### APP002: アプリ間依存はインターフェース経由のみ
- **決定**: アプリ間の依存は consumer-defined interface（facade パターン）を使用
- **根拠**: Go の「accept interfaces, return structs」イディオムに合致。アプリ内モジュール間は直接参照を許可

### APP003: パッケージ深さ 5 階層の許容
- **決定**: `apps/{app}/{module}/internal/store/` の 5 階層を許容（通常の 4 階層制限を緩和）
- **根拠**: 追加の 1 階層は純粋な名前空間グルーピングであり、認知的複雑さを増さない

### APP004: 同一アプリ内モジュール間の直接参照
- **決定**: 同じ apps/ 配下のモジュール間はサービス直接参照を許可
- **根拠**: `internal/` による Go コンパイラレベルのアクセス制御が保証するため

### APP005: アプリ単位のマイグレーション分割
- **決定**: `db/migrations/{app_name}/` でアプリ単位に分割可能とする
- **根拠**: 大規模プロジェクトでのマイグレーション管理を容易にする

## 現在のステータス

Phase 1 では `modules/` のみを使用（ADR-M006）。本提案は apps/ 導入時の設計指針として保持する。
